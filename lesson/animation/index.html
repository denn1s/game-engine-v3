Time, Eased — The Animation Lab

All semester, state has changed instantly: a key flips a number and the number is already different. Today the engine learns that a value can travel — that an animation is not a process but a pure function of elapsed seconds. We build the machinery in a throwaway lab, then name the two places the game is about to demand it: the pack reveal and the walk cycle.

The one idea

Everything in this class hangs from a single sentence — say it out loud at 0:00 and revisit it at every beat:

An animation is a  value = f(elapsed seconds)  — and a system's only job is to feed it time.
kindquestion it answersthe formulalab tab
clip (frame anim)which picture of the strip?frame = floor(t · N/D) % N + 12, 3, 5
tween (property anim)what number right now?value = from + (to−from) · ease(t/D)4, 5

Two different outputs, the same input: seconds. That's why they compose on one entity in tab 5, and why real engines (Unity's Animator, Godot's AnimationPlayer, Bevy's animations) store keyframe tracks as data sampled by time — exactly what we're hand-rolling at jam scale. The components in our lab literally hold only t; ask the overlay to prove it.

Why "seconds", out loud

The machine you build it on is not the machine they run it on. love.update(dt) hands every system the frame's real length — 1/144 s on a student's gaming laptop, 1/60 on the projector, a stutter's 1/25 in between. "Frame = frame + 1" per update makes the walk cycle run at whatever the framerate happens to be. This class has already been bitten once: lesson 08's typewriter advanced one character per frame no matter what speed said, exactly this bug wearing a trench coat. The table the day loop wrote then, the whole class writes now.

What's in the way

Read from the class repo as it stands at the end of lesson 11. The engine is healthy — resources, event entities, the four system hooks, Screen at 640×400 — and it has exactly one time-shaped hole.

src/systems/FadeRenderSystem.lua

Our only animation is linear. The fade computes alpha as a raw fraction of its clock — correct, but robotic. The pattern (accumulate dt, sample a function) is already right; today we make the function replaceable.

src/ecs/Registry.lua

There is no "time" concept — on purpose. No Timeline, no coroutine, no after(). Today proves the engine doesn't need one: dt is already a parameter of every update, and components can hold a number. That's the whole substrate.

Cards appear instantly. The pack reveal (next class) is five cards that must arrive: slide in, flip, settle. The walk cycle (the class after) is a sprite that must step. Both are consumers of whatever we build here.

Live-code the clip — start with the wrong version

Write the naive thing first, on purpose:

-- v1: the frame is the clock (WRONG — type this live, run tab 2)
sprite.frame = sprite.frame % 4 + 1        -- once per update()!

It "works" — then open the overlay's frame-time plot or tab out, and the walk halves/doubles its speed. That's the bug from the framerate table, live in ninety seconds. Now fix it honestly: the clip knows frames and seconds; floor() converts; the modulo loops.

-- src/anim/SpriteClip.lua   ← pure, no LÖVE, testable
function SpriteClip.frameAt(clip, t)
    local looped = t % clip.duration
    return math.floor(looped * SpriteClip.fps(clip)) % clip.frames + 1
end

-- src/systems/ClipAnimationSystem.lua   ← the only consumer of dt
for _, sprite, anim, demo in registry:each("sprite", "clipAnim", "demo") do
    if demo.n == lab.demo then
        anim.t = anim.t + dt
        sprite.frame = SpriteClip.frameAt(anim.clip, anim.t)
    end
end

Pause on the split. The math module has never heard of entities; the system has no opinions about easing or quads; the renderer didn't change at all. That's the atomic-systems principle doing its job — three files, each explodable alone. Tab 3 then comes for free: three entities, three durations, zero new code. Say it: "a data-driven design is when a feature ships as a table."

Live-code the tween — a value with a deadline

Same disease, property version: x = x + 300*dt "works" until something else needs that square to arrive at a moment gameplay depends on (the card is playable when it lands!). Distance-per-second is an excuse; a deadline is the design. So the API inverts: give me from, to, and when:

-- src/anim/Tween.lua — one pass, then it holds
function Tween.at(tween, t)
    local p = t / tween.duration
    if p < 0 then p = 0 elseif p > 1 then p = 1 end
    return tween.from + (tween.to - tween.from) * tween.easing(p)
end

Then the curve: write linear, ask the room for "starts fast, ends soft" — collect t·(2−t) — then "what about past the target and back?" and drop outBack in as a constant they'll look up rather than derive. Press the race button on the figure. The lanes of tab 4 are the same three functions; the test line that makes it architecture and not vibes:

assert(near(Tween.at(trip, 2.0), 520), "tween missed its arrival")
assert(Tween.at(trip, 1.5) > 520,     "outBack should overshoot mid-trip")

Celeste Hearthstone Point out that outBack overshoots past the endpoint — the value briefly exceeds the target. That terrifies people shipping it into gameplay logic, which is the exact reason arrival is asserted at p = 1, not near it. Feel lives in presentation; gameplay reads the component after the system writes it — the same firewall the lab's readout shows live.
