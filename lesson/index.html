Game Engine Architectures

Part 1 — Six answers to one question: where does behavior live?

You just shipped a Breakout with no particular architecture — and it works. So why do engines obsess over architecture? Because games are the software that changes the most: every day of development someone adds a power-up, an enemy, a cutscene, a bicycle. An architecture is a bet about which changes will be cheap. Today we look at the six bets the industry has made, in roughly the order it made them — each one born from the previous one's pain.

How each mini-lesson works. For every architecture: the idea → the same Pong, rebuilt (lesson/pong/0X-name/, ~150 lines each, only the architecture changes) → the same idea at scale in a Pokémon-style game → and two questions for you: one this architecture breezes through, one that makes it suffer. Plus one recurring test in every round: 🚲 the bicycle — the player walks, now add a bicycle that's faster, changes the sprite, and can jump small gaps.

1 / 6

Procedural — "just make it work"

behavior lives in the update loop — all of it
every game jamAtari-era gamesyour Breakout, probablyPICO-8 carts

The idea

The game is a bag of variables, mutated top-to-bottom by one update function, once per frame. There is no architecture — and at this size that is honestly fine: it's the fastest path to a working game, you can read the whole frame like a recipe, and every value is one print() away.

Pong

love lesson/pong/01-procedural 
-- ball vs left paddle (AABB, written out longhand)
if ballVX < 0 and ballX < 42 and ballX > 18
    and ballY + 12 > leftY and ballY < leftY + 80 then
    ballX = 42
    ballVX = -ballVX * 1.06
    ballVY = ((ballY + 6) - (leftY + 40)) / 40 * 240
end

-- ball vs right paddle (same thing again — copy, paste, flip)
if ballVX > 0 and ballX + 12 > 918 and ballX < 942
    and ballY + 12 > rightY and ballY < rightY + 80 then
    ...

Notice: the state of "a ball" is four loose globals. The idea of a ball exists only in your head. Before you scroll on, try it: how would we add a second ball? There is no ball to make another of.

The same idea, Pokémon-sized

battle.lua — 12,000 lines
doMove() calcDamage()  if id==25 then ... elseif id==26 then ... drawSprite()  if id==25 then ... canEvolve()  if id==25 then ... drawBattleUI()
globals: enemyHP, playerMon, turnPhase, menuDepth, weather, …
What a Pokémon is, is smeared across every function that ever needed to know. Fun fact: Gen 1 Pokémon was close to this — hand-written assembly with data tables, and famously full of bugs (Missingno. is what happens when data and code have no boundary).
😌 Easy round: "make Thunderbolt 10% stronger"

One constant, one line, done in 30 seconds. No layers to dig through, no indirection: for tweaks, nothing beats a pile of plain code. This is why jam games and prototypes are written this way — when the whole game changes daily, boundaries just slow you down.

😖 Hard round: "add Pokémon #152"

Which files do you touch? All of them. Every if id == ... chain in damage, sprites, evolution, cries, AI — each one grows by a case, and missing one is a silent bug. The content is the code, so adding content means editing everything. 151 Pokémon × this = the reason architectures exist.

🚲 The bicycle test

if onBicycle then ... end — sprinkled into movement, animation, encounter rate, collision ("can't ride indoors"), audio. Each new mode (surfing? running shoes?) multiplies the conditions in every one of those places. Mode × feature = combinatorial scatter.

Shines at

  • Speed to first playable — nothing is faster
  • Total transparency: the frame reads top to bottom
  • Trivial debugging: all state is right there

Breaks at

  • Adding content: data is fused into code
  • Two of anything (second ball, second player)
  • More than one person editing the file
2 / 6

OO Inheritance — "everything IS-A"

behavior lives in the class of each object
Unreal's AActor → APawn → ACharacterlate-90s / 2000s C++ enginesJava game tutorials forever

The idea

Objects own their data and their behavior, and share code by inheriting from a parent. This was the game architecture for a decade, and it maps beautifully onto how we speak: a Ball is a MovingEntity is an Entity. Now a ball is a real thing: Ball.new() gives you a second one for free.

Pong

love lesson/pong/02-inheritance 
--  Entity                   x, y, w, h — exists, can be drawn
--  └── MovingEntity         + vx, vy — moves every frame
--      ├── Paddle           + reads keys, clamps to court
--      └── Ball             + bounces off walls, speeds up

function Paddle:update(dt)
    self.vy = 0
    if love.keyboard.isDown(self.upKey) then self.vy = -360 end
    if love.keyboard.isDown(self.downKey) then self.vy = 360 end
    MovingEntity.update(self, dt) -- the "super" call
    self.y = math.max(0, math.min(540 - self.h, self.y))
end

But look what's still sitting in love.update:

-- collision BETWEEN objects belongs to NEITHER class.
-- It leaks right back into main:
if ball.vx < 0 and ball:overlaps(leftPaddle) then
    ball:bounceOff(leftPaddle)
end

Now try to place this: where does a PowerUp that drifts like a Ball but is steered like a Paddle go? The hierarchy is a tree. Abilities don't come in trees.

The same idea, Pokémon-sized

Pokemon
├── FirePokemon
│   └── Charmander ── Charmeleon ── Charizard   ... ×151 leaf classes
├── WaterPokemon
│   └── Squirtle ── Wartortle ── Blastoise
└── ElectricPokemon
    └── Pikachu ── Raichu

Move
├── PhysicalMove ── Tackle, Earthquake ...
├── SpecialMove ── Thunderbolt, Surf ...
└── StatusMove ── Sleep Powder, Growl ...
The game modeled by identity: every species is a class, every shared behavior lives in some ancestor. Each Pokémon slots into exactly one branch of the tree.
😌 Easy round: "add Raichu, an evolved Pikachu"

Subclass, override the stats and the sprite, inherit everything else. One new file, zero existing files touched. When new content really is "an existing thing, but slightly different," inheritance is genuinely elegant — that's why UI toolkits still use it.

😖 Hard round: "Lanturn is Water AND Electric"

Pick a parent. Duplicate the other type's behavior into it. Now fix the copy every time the original changes. Multiple inheritance "solves" this and brings the diamond problem instead. The deeper issue: type is not identity, it's a property — and properties want to be composed, which is the next architecture. (This exact pain is why the industry moved on: see "Evolve Your Hierarchy," the 2007 essay that popularized components.)

🚲 The bicycle test

BicyclePlayer extends Player? Then mounting means destroying the player object and constructing another one, copying all state across, mid-frame. Add SurfingPlayer and every pair of modes needs a transition. Modes are not identities either.

Shines at

  • "Same but different" content via subclassing
  • Readable call stacks; behavior next to data
  • Matches how designers talk about game objects

Breaks at

  • Combining abilities across branches (class explosion)
  • Objects that change nature at runtime
  • Cross-object logic still homeless (collision, scoring)
3 / 6

Component-based — "everything HAS-A"

behavior lives in component objects attached to game objects
Unity GameObject / MonoBehaviourUnreal ActorComponentsGTA's RenderWare (2000s)

The idea

Kill the hierarchy. A GameObject is an empty shell with a position; you build behavior by adding parts — a renderer, a mover, an input reader. Last section's impossible PowerUp is now just a new combination of existing parts. This is Unity's model, and it's the single most-used game architecture in the world.

Pong

love lesson/pong/03-components 
-- composition instead of classes: a paddle IS the sum of its parts
GameObject.new(scene, "paddle", 30, 230, 12, 80)
    :addComponent("renderer", RectRenderer())
    :addComponent("control", KeyboardControl("w", "s"))

GameObject.new(scene, "ball", 474, 264, 12, 12)
    :addComponent("renderer", RectRenderer())
    :addComponent("motion", Motion(320, 60))
    :addComponent("bounce", BounceWalls())
    :addComponent("ballLogic", BallLogic())

Each component still carries its own update() — logic and data travel together, and components find each other by lookup:

local function BounceWalls()
    return {
        update = function(self)
            local go = self.gameObject
            local motion = go:getComponent("motion") -- find my sibling
            if go.y < 0 then go.y, motion.vy = 0, -motion.vy end
            ...

This is NOT yet ECS — remember this slide when someone says Unity is an ECS. Three tells: components have methods; each object updates its own parts; components talk through getComponent/findByTag searches. And note who keeps the score in our Pong: an invisible GameObject called manager — the empty-object-with-a-manager-script that every Unity project on Earth contains. Match flow had nowhere to live, so we invented a ghost to haunt it.

The same idea, Pokémon-sized

GameObject "Pikachu"
StatsSprite MoveSetStatusCondition ShinyPalette ← just add it
GameObject "Trainer Red"
SpritePartyBattleAISightLine
The game modeled by parts: a Pokémon and a trainer are wildly different things built from the same kit, and each part updates itself. Nothing stops you inventing a new combination — a wild Pokémon that fights back on the overworld is just Stats + Sprite + BattleAI.
😌 Easy round: "make this one shiny"

Swap the Sprite component's palette, or attach a ShinyPalette component. No hierarchy to renegotiate, no other object touched. Per-thing variation is where composition earns its keep — this is why Unity's Inspector is drag-and-drop parts.

😖 Hard round: "who runs the battle?"

Turn order needs both Pokémon's speed stats. Damage needs the attacker's stats, the defender's types, the weather, and the item slots. No single object owns any of this, so it lands on the invisible BattleManager — a procedural program (architecture #1!) wearing a component as a disguise. Bonus pain: whose update() runs first, and what happens when the answer matters? (Unity's answer is a settings panel called Script Execution Order. Yes, really.)

🚲 The bicycle test

Nice: swap WalkMovement for BicycleMovement, swap the sprite component, done — first architecture where the bike is pleasant. Small print: every component that cached getComponent("walkMovement") now holds a dead reference, and gap-jumping needs BicycleMovement to talk to the collision component. Sibling wiring is your job.

Shines at

  • Mixing abilities freely — no class explosion
  • Per-object variation (designers can compose in an editor)
  • Reusable parts across wildly different objects

Breaks at

  • Cross-object rules → god "manager" objects
  • Implicit update order between components
  • getComponent spaghetti at scale
4 / 6

Event-driven — "don't call us, we'll call you"

behavior lives in subscribers
Godot signalsUnreal delegatesC# events in Unityevery UI framework ever

The idea

Less an architecture, more a dimension that cuts across all the others: instead of A calling B, A announces a fact on a bus and whoever cares reacts. The simulation only detects; the rules react. The ball does not know scoring exists. Scoring does not know what a ball is.

Pong

love lesson/pong/04-events 
-- the simulation DETECTS and announces. It decides nothing:
if ball.x < -ball.w then Bus.emit("ball:out", "left") end

-- the rules are REACTIONS, registered elsewhere:
Bus.on("ball:out", function(side)
    if side == "left" then match.right = match.right + 1
    else match.left = match.left + 1 end
    Bus.emit("match:point", side)   -- chains are normal here
end)

-- juice, added later, touching NOTHING above:
Bus.on("ball:paddle", function() flash.time = 0.08 end)
Bus.on("match:point", function() print("beep!") end)

Those last two lines are the whole pitch: screen flash and sound were added without touching the simulation. Now the trap — try answering this yourself: "what happens when the ball goes out?" You can't do it by reading top to bottom anymore. One point is a chain: ball:out → match:point → serve or match:over. You don't read event-driven code; you grep it.

The same idea, Pokémon-sized

the event bus
MoveUsedDamageDealtPokemonFaintedTurnEndedWeatherChanged
subscribers = the actual game rules
ability Static: on DamageDealt(contact) → 30% paralyze item Focus Sash: on DamageDealt → survive at 1 HP healthbar UI: on DamageDealt → animate weather: on TurnEnded → tick
Read a real Pokémon ability description. They're all "WHEN X happens, DO Y" — abilities literally ARE event handlers.
The game modeled by reactions: the battle core announces facts, and abilities, items, UI and weather each hang their rule on the bus — none of them knowing the others exist.
😌 Easy round: "add the ability Static"

"When hit by a contact move, 30% chance to paralyze the attacker" — that sentence is the code: one subscriber on DamageDealt. No other system touched. Reactive, cross-cutting rules (abilities, items, achievements, tutorials, analytics) are exactly what events are for.

😖 Hard round: "why did it faint before the Sash triggered?"

Because the faint-check handler ran before the item handler, and nothing in the code says which comes first. Event systems trade visible control flow for implicit ordering — and cascades (events emitting events emitting events) mean a single wrong order surfaces three reactions later. Sequential logic — a battle turn is strictly sequential! — fights this model. Detect with events; sequence with something else.

🚲 The bicycle test

Emit player:mounted; movement, sprite, music each react in their own corner. Decoupled and pretty — but "what does mounting do?" is now answered nowhere. The behavior is smeared across handlers, discoverable only by grep.

Shines at

  • Reactive rules: abilities, items, achievements
  • Adding juice/UI/audio with zero coupling
  • Letting strangers extend the game (mods!)

Breaks at

  • Sequential flow (a battle turn) as a chain of events
  • Debugging cascades and handler order
  • "Who changed this value?" — someone, somewhere
5 / 6

Scene graph — "the game is a tree"

behavior lives in nodes, arranged in a tree
Godot (Node2D/Node3D)Flash display listcocos2devery UI toolkit, again

The idea

Everything is a Node with a position relative to its parent. Update and draw walk the tree; each node applies its transform before its children draw. Move a parent and its whole subtree moves — transform propagation, the superpower here. Behavior = subclass a node and override process(). This is Godot, top to bottom.

Pong

love lesson/pong/05-scenegraph 
root
├── court                 <- shakes on every paddle hit
│   ├── leftPaddle ── rect    (in Godot: Sprite2D + CollisionShape2D)
│   ├── rightPaddle ── rect
│   └── ball ── rect
└── ui                    <- NOT under court: doesn't shake
    ├── leftScore
    └── rightScore
-- the court's ONLY behavior is shaking. Every game object is its
-- child, so two numbers move the entire world:
function CourtNode:process(dt)
    self.shake = math.max(0, self.shake - dt)
    if self.shake > 0 then
        self.x = love.math.random(-4, 4)
        self.y = love.math.random(-4, 4)
    else
        self.x, self.y = 0, 0
    end
end

Run it and hit the ball: the court shakes, the score doesn't. That's an architectural decision expressed as where a node sits in a tree — wonderfully direct. Meanwhile the ball finds the paddles by path, self.parent:get("leftPaddle") — Godot's get_node("../LeftPaddle"), string-typed and one rename away from a crash.

The same idea, Pokémon-sized

World
├── Map ── TallGrass, Ledges, Water
├── NPCs ── TrainerJoey (drop-in subtree: Sprite + SightLine + Dialog)
├── Player ── Sprite, Camera
└── UI ── Menu, Dialog box
The game modeled by place: everything on screen is a node, positioned relative to its parent. The camera rides the player, dialog boxes ride the UI branch, and a trainer is a reusable subtree you can drop onto any map.
😌 Easy round: "add a trainer to route 30"

Build the trainer once as a subtree (sprite + sight-line + dialog), save it as a reusable scene, and drop instances anywhere on any map. Composition of trees is Godot's whole workflow, and it's a genuinely great way to build worlds and UI — spatial things, made of spatial parts.

😖 Hard round: "where does the party live?"

Six Pokémon that exist while walking, battling, in menus, and across save files — but are drawn in none of those places. They have no position, no parent, no visual: the tree has no natural slot for pure state. Every scene-graph engine sprouts a global-state escape hatch (autoloads in Godot, DontDestroyOnLoad in Unity) — which is the architecture admitting the model doesn't cover everything.

🚲 The bicycle test

Swap the Sprite child, keep the Player node. Decent — but speed and gap-jumping live in the Player's process(), so modes end up as if bicycle flags inside one script (hello, architecture #1) or as swapping behavior-nodes in and out of the tree at runtime.

Shines at

  • Anything spatial: camera shake, attach, parent/unparent
  • Building worlds & UI from reusable sub-scenes
  • Draw order and grouping fall out for free

Breaks at

  • Non-visual state (inventory, progress) has no home
  • Cross-branch logic → string paths everywhere
  • Deep trees hide "who moves whom"
6 / 6

ECS — "entities have data, systems do things"

behavior lives in systems that run over data
entt / flecs (C++)Bevy (Rust)Unity DOTSOverwatchthe rest of this course

The idea

Looks like components, but flips who is in charge. Components become plain data — no methods, no update, just tables. An entity is just a number: a key into the component stores. And ALL logic moves into systems, each of which queries "every entity with components X and Y" and processes them in bulk. Architecture #3 asks "what does this object do this frame?" ECS asks "what does the movement rule do to everything, this frame?"

Pong

love lesson/pong/06-ecs 
-- a paddle is not a class: it's this recipe of components
registry.spawn({
    position = { x = 30, y = 230 }, size = { w = 12, h = 80 },
    velocity = { vx = 0, vy = 0 },
    paddle = { upKey = "w", downKey = "s" },
})

-- moves ANYTHING with position + velocity — paddles, balls,
-- and every entity you haven't invented yet:
local function movementSystem(dt)
    for _, entity in ipairs(registry.query("position", "velocity")) do
        local position = registry.get(entity, "position")
        local velocity = registry.get(entity, "velocity")
        position.x = position.x + velocity.vx * dt
        position.y = position.y + velocity.vy * dt
    end
end

The demo: press B during play. Each press spawns another ball — and movement moves it, walls bounce it, paddles hit it, scoring scores it, with zero new code. Now flip back to architecture #1, where a second ball was unthinkable. Same game. That gap is what an architecture buys. (Systems never call each other — they meet only through the data. And storing "all positions together" is the data-oriented, cache-friendly layout that makes ECS fast in C++ — same shape you'll see in entt.)

The same idea, Pokémon-sized

the registry (overworld)
position[ ]sprite[ ] encounterZone[ ]sightLine[ ] player[ ]bicycle[ ] ← one new store
systems
MovementSystemEncounterSystem TrainerSightSystemAnimationSystem BicycleSystem ← one new system
500 NPCs, 3,000 tiles of grass, particles — bulk processing of uniform stuff is ECS's home turf.
The game modeled by data: the overworld is component stores plus a handful of systems, and a new mechanic is one new store and one new system — every existing system carries on untouched.
😌 Easy round: 🚲 the bicycle — finally at home

Add a bicycle component to the player; a BicycleSystem adjusts speed and handles gap-jumps; the animation system queries it to pick the sprite. Dismount = remove the component. Surfing? A surf component, same recipe — modes compose instead of multiplying. This is the pattern you'll use for cards, buffs, and status effects all semester.

😖 Hard round: "add one more trainer battle"

The battle is sequential flow, menus, and script — two combatants, no bulk, nothing to query. Forcing it into systems gives you systems-of-one that secretly form a state machine. The honest answer: don't force it. The overworld is a great ECS scene; the battle is a different scene, better served by a state machine over plain data tables. Which raises the real question: can one game mix architectures? Every shipped one does — that's next class.

Shines at

  • Ability/mode composition: add a component, add a system
  • Crowds of uniform things — and cache-friendly speed
  • New content = new data, not new code paths

Breaks at

  • Sequential flow: turns, menus, cutscenes
  • "What does the player do?" is smeared across systems
  • Ordering bugs between systems (you'll meet these in the lab)

📺 Assigned watching: Overwatch Gameplay Architecture and Netcode (GDC 2017) — a shipped AAA game on real ECS. Watch for how much of the talk is about discipline: system ordering, where "manager" logic is allowed to live, and what they do when something doesn't fit the model.

Read the rows and notice two things. First: no row is all green. Not even ECS — an architecture is a bet about which changes will be cheap, and every bet loses somewhere. Anyone who tells you their architecture has no red cells hasn't shipped with it yet.

Second: the columns don't compete — a real game needs several of them cheap at once, in different places. Overworld: crowds and composition → ECS. Abilities and items: reactions → events. UI and camera: spatial trees → scene graph. Battle flow: sequential → a plain state machine. Which is why…

Every shipped engine is a hybrid. Unity = components + events + a scene tree + optional ECS (DOTS). Unreal = deep inheritance + components + delegates + a data-driven scripting layer (Blueprints). Godot = scene graph + signals — and a written manifesto on why it rejects ECS. In Part 2 we dissect all three as compositions of what you learned today: which paradigms they mixed, why, and what each bet cost them.

And your lab: you'll rebuild your Breakout on ECS — bricks, balls, power-ups: crowds of uniform things with composable abilities. Look at the table: that's the green column territory. Now you know why it's the right tool for that job — and you'll know when it isn't.
