An entity is just a number. An ID. No fields, no methods, no class. It exists only as a key that other tables remember.

C
position { x = 240, y = 135 }

A component is plain data attached to an entity. A little table of values. It can't do anything — and that's the point.

S
MovementSystem query(position, velocity)

A system is a function that runs every frame over every entity matching its query, and does exactly one job.

01 · the problem

The wall every class tree hits

In lesson 01, Pong was a handful of classes and life was good. Classes stop being good the moment the design changes underneath them. Say the designer wants a power-up: a ball that a player can briefly steer.

The tree keeps answering "what is this thing?" — but gameplay keeps asking "what does this thing have?" Can it move? Can it be steered? Does it bounce? Those are checkboxes, not ancestry.

02 · the idea

Tip the objects 90° — your game is a table

Take the objects and rotate them: every field becomes a column, every instance becomes a row, and every method becomes homeless. On purpose — behavior moves out of the objects entirely.

Notice what happened to SteerableBall: it's not a new class. It's just a row that has ball and a steering component. The wall from section 01 isn't climbed — it never existed.

05 · the payoff

Why engines keep reinventing this

Behavior is a checkbox

A new ability = a new component + one system that queries it. No tree surgery, no refactor. Any entity can have any mix — designers compose, programmers write systems.

ball + steerable = the power-up from section 01

Systems don't know each other

MovementSystem never calls BounceSystem. They only share the table. You just proved it above: delete any system and the rest keep working. Debugging means reading rows, not chasing call stacks.

Movement → position velocity ← Bounce

Rows the CPU loves

All positions live together, all velocities live together. Tight loops over same-shaped data prefetch beautifully — the data-oriented layout from week 1. This is why Overwatch and Unity DOTS bother.

objects scattered on the heap
one component store — every position, back to back

And the honest counterweight: ECS is a tool, not a religion. For UI, tools, and tree-shaped problems it can be the wrong shape — Godot says so at length, and lesson 07's hybrid Pong is the peace treaty.

06 · back to code

You already own one

You built this exact machine in lesson 02. The whole registry is ~100 lines of Lua — here is its beating heart, src/ecs/Registry.lua:

-- one table per component TYPE, indexed by entity:
-- components = { position = { [1]={x=30,y=230}, [3]={x=473,y=263} }, ... }

function Registry:spawn(components)
    local entity = self.nextEntity          -- an entity is just a number
    self.nextEntity = entity + 1
    for name, data in pairs(components) do
        self:add(entity, name, data)
    end
    return entity
end

function Registry:query(...)                -- "every row where ALL columns are filled"
    local names = { ... }
    local result = {}
    for entity in pairs(self.components[names[1]] or {}) do
        local ok = true
        for i = 2, #names do
            local store = self.components[names[i]]
            if not store or store[entity] == nil then ok = false; break end
        end
        if ok then result[#result + 1] = entity end
    end
    table.sort(result)
    return result
end
