Game Engine Architectures

Part 2 — Every shipped engine is a hybrid: Unity, Unreal and Godot as compositions of what you already know.

Last class ended on a table with no all-green row: every paradigm is bad at something. Six paradigms, six bets:

#1 procedural — the update loop #2 inheritance — the class #3 components — attached parts #4 events — subscribers #5 scene graph — the tree #6 ECS — systems over data

So what does a team betting hundreds of engineer-years do? They don't pick one. They pick a core bet — the paradigm the whole engine is organized around — then layer the others on where the core is weak, and cut an escape hatch for whatever still doesn't fit. Today we dissect the three engines you've used as exactly that: a core, layers, and escape hatches. Once you see the pattern, their weirdest features stop being arbitrary — they're patches over some paradigm's red cell.

One new ingredient first. All three engines lean hard on something Part 1 only brushed against: data-driven design — content lives in data files (prefabs, Blueprints, scenes, tables) that non-programmers create and edit, and the code just instantiates them. It's not a seventh place for behavior to live; it's the answer to the "Pokémon #152" column: adding content should mean adding data, never code. Watch how each engine builds its whole editor around this idea.

Under the fancy UI: the layer cake

Before dissecting each engine, strip away the editor, the gizmos, the profilers. What is actually running when you press Play? Every engine on this page — and yours — is the same four-layer cake:

                 ┌─ THE EDITOR ─────────────────────────┐
                 │ a separate program! It uses the same  │
                 │ engine to draw its viewport, and its  │
                 │ real job is writing the data files →  │
                 └───────────────────────────────────────┘
┌────────────────────────────────┐      ┌────────────────────────┐
│ 4 YOUR GAME                    │ ←──  │ DATA FILES             │
│   scripts, gameplay rules      │ load │ prefabs, .tscn, tables │
├────────────────────────────────┤      └────────────────────────┘
│ 3 OBJECT MODEL                 │  GameObjects / Actors / Nodes —
│   the paradigms live here      │  everything Part 1 was about
├────────────────────────────────┤
│ 2 NATIVE CORE                  │  the loop, renderer, physics,
│   C/C++, performance-critical  │  audio, asset loading
├────────────────────────────────┤
│ 1 PLATFORM                     │  OS, SDL, Vulkan/GL/DirectX
└────────────────────────────────┘
The frame loop from lesson 00 — while true: input, update, draw — still exists in every one of these engines. It just lives in layer 2 now, and calls you: that inversion of control is the single biggest difference between using a library and using an engine.

And here's the part that should make this course click: you already own most of this cake. LÖVE is layers 1–2 (SDL and a C++ core with the loop, calling your love.update), Lua is layer 4 — and layer 3, the object model, is exactly what you've been building by hand: the registry, the scene, the systems. An engine is not magic. It's this diagram with more engineers.

What differs per engine is how layer 3 is built and how layers talk — so each section below now ends with that engine's cake, under the hood.

ENGINE 1/3

Unity — the composition bet

core bet: components (#3), made in 2005
Hollow KnightCupheadAmong Us~⅔ of mobile games

The bet

Unity launched in 2005, when the industry standard was Unreal-style C++ inheritance — and it bet against that standard on two ideas: behavior comes from attaching parts, not deriving classes (Part 1's architecture #3, almost verbatim), and the editor is the engine — designers compose GameObjects by drag-and-drop, save them as prefabs (data-driven!), and never see a compiler. That accessibility bet is why Unity, not Unreal, ate the indie and mobile world.

How it grew

Watch the pattern: every addition below is a patch over a specific pain the core bet couldn't handle.

  • 2005Unity 1.0 ships — Mac-only! — with the core bet already whole: GameObjects, attachable scripts, compose in the editor, prefabs making content data-driven from day one. #3 + data-driven
  • 2008Unity iPhone — the accessibility bet meets the App Store. The mobile explosion funds everything that follows. Not an architecture change — but it's why this architecture became the world's default.
  • ~2010sthe folklore layer — GameManager objects and the Script Execution Order panel become standard practice. #1 leaks in Pain: cross-object rules and update ordering have no home in pure composition. The community patched it with conventions before Unity patched it with features.
  • 2014UnityEvents ship with the new UI system: designers wire reactions in the Inspector, no code. #4 events Pain: "when X happens, do Y" kept requiring a programmer.
  • 2017DOTS announced ("performance by default"). #6 ECS Pain: MonoBehaviour's per-object updates hit a hard ceiling on crowds and simulation-heavy games.
  • 2023Entities 1.0 finally lands — six years after the announcement, opt-in, not core. Retrofitting a paradigm into an ecosystem takes longer than building the ecosystem did.

The composition

the core: GameObject + MonoBehaviour #3 components
An empty shell + attachable scripts, each with its own Update(). Our lesson/pong/03-components is a 100-line Unity.

Under the hood

Unity's secret is that it's two programs: a closed-source C++ engine, and your C# code running in a VM beside it — with a bridge in between that every call crosses.

┌─ C# WORLD (Mono VM, or IL2CPP AOT) ───────────────────────┐
│  your MonoBehaviours — Update() invoked BY the engine     │
│  your C# GameObject is a handle: the real one lives below │
│  garbage collector here → the famous GC hitches           │
├─ the native↔managed bridge — every crossing has a cost ──┤
│                                                           │
│  PlayerLoop (theirs, not yours):                          │
│    input → FixedUpdate×N + physics (PhysX) → Update       │
│          → animation → LateUpdate → render                │
│  GameObject, Transform actually live HERE, in C++         │
│  asset database · renderer · audio                        │
└─ C++ WORLD (closed source) ───────────────────────────────┘
Explains three folklore rules at once: why touching transform in a loop is slow (bridge crossings), why everyone pools objects (the C# garbage collector), and why DOTS exists — it moves your data below the bridge, where the loop can chew it in bulk. LÖVE has the same anatomy: C++ core, your Lua called across a boundary, 60 times a second.

Real code

// Paddle.cs — attach this to a GameObject in the editor
public class Paddle : MonoBehaviour {          // a part with logic: #3, verbatim
    public float speed = 360f;                 // shows up in the Inspector (data-driven)
    public UnityEvent onBallHit;               // designers wire reactions here: #4

    void Update() {                            // every object updates its own parts
        float dir = Input.GetAxisRaw("Vertical");
        transform.Translate(0, dir * speed * Time.deltaTime, 0);
    }                                          // transform = a node in a tree: #5
}

Four paradigms in ten lines — count the tags. You already wrote this class in Lua two weeks ago.

❓ "So… is Unity an ECS engine?"

No. Run the three tells from Part 1: MonoBehaviours carry logic (components should be plain data), each object updates its own parts (systems should process in bulk), and they find each other with GetComponent (systems should query). That's architecture #3, not #6. The confusion is so common precisely because "component" appears in both names — now you're immune to it.

❓ "Then what is DOTS, and why did it take from 2017 to 2023 to ship?"

DOTS is real ECS (architecture #6) — plain-data components, systems, queries, cache-friendly storage — built for the workloads where MonoBehaviour hits a wall: crowds, simulations, thousands of uniform things. It was announced in 2017 and reached 1.0 in 2023, after years of preview rewrites. Why so brutal? Because retrofitting a new core paradigm into an engine is fighting the engine's entire gravity: twenty years of tutorials, every Asset Store package, every team's habits, and every editor workflow assume MonoBehaviour. The result: DOTS ships as an opt-in escape hatch for hot paths, not a replacement. Architecture choices are nearly irreversible at engine scale — that's why this class exists.

❓ "Why does every Unity project have a GameManager?"

Part 1, components, hard round: cross-cutting rules (match flow, turn order, win conditions) have no object to live on, so every project invents an invisible GameObject with a manager script — a procedural program (architecture #1) wearing a component costume. Unity never gave flow logic a first-class home, so the community standardized the workaround. Related smell: when the order of component updates matters, the fix is a settings panel called Script Execution Order. When your architecture needs a settings panel to sequence itself, that's a red cell showing through.

The bet bought them

  • Compose-in-editor: designers build without compiling
  • Gentlest learning curve of the big three
  • The Asset Store: parts are tradeable, an economy of components

The bet cost them

  • Flow logic homeless → manager sprawl
  • Implicit update order between thousands of scripts
  • Performance ceiling → the six-year DOTS retrofit
ENGINE 2/3

Unreal — the layered bet

core bet: inheritance (#2), made in 1998 — then never undone
FortniteGears of WarFinal Fantasy VII Remakebasically all AAA third-party

The bet

Unreal Engine 1 shipped in 1998, when deep C++ inheritance was simply how games were made — and it committed hard: AActor → APawn → ACharacter is a chain your students can still open in UE5 today. But Unreal made a second bet nobody else made in 1998: a scripting layer for designers (UnrealScript then, visual Blueprints now), so gameplay could be authored without touching the C++ core. Everything since has been layers: components bolted on, delegates for events, data assets everywhere. Unreal is not one architecture — it's 25 years of architectures, stacked, with backward compatibility as the prime directive. That's the honest answer to "why is Unreal so complex."

How it grew

  • 1998Unreal Engine 1 — two bets at once: a deep C++ Actor hierarchy for the engine, and UnrealScript on top so modders and designers could write gameplay without touching it. #2 + scripting layer The scripting layer is why Unreal mods (and half the industry's designers) exist.
  • 2006UE3: Kismet — visual scripting for level logic; designers click boxes together instead of filing tickets. data-driven, visual Pain: gameplay iteration was bottlenecked on programmers.
  • 2014UE4 — UnrealScript is deleted after 16 years, replaced by Blueprints (Kismet grown up) plus exposed C++; ActorComponents get promoted to first-class. #3 components Pain: the hierarchy was too rigid for cross-branch abilities — the exact hard round from Part 1. Also proof a paradigm CAN be removed: at the price of breaking every project in existence.
  • 2022UE5: Mass Entity — an opt-in ECS layer, debuted moving the crowds of the Matrix Awakens city demo. #6 ECS Pain: ten thousand pedestrians do not want to be Actors.

The composition

the core: the Actor hierarchy #2 inheritance
AActor → APawn → ACharacter — derive your player from ACharacter and inherit walking, jumping, networking, replication. "Same but different" at its industrial best.
layered on top
ActorComponents #3 components delegates / dispatchers #4 events component attachment, World Outliner #5 tree Blueprints, DataTables data-driven
the escape hatches
GameMode / GameState flow, first-class! Mass Entity (UE5) #6 ECS
Note GameMode: Unreal is the only one of the three that gives match flow a dedicated class instead of a community workaround. Decades of shipped shooters taught them.

Under the hood

Unreal is one giant open-source C++ program — but C++ is hostile to gameplay iteration (compile times, manual memory, no reflection). Unity's answer was to bolt a C# VM beside the engine; Unreal's answer is stranger: it grew a managed language inside C++.

┌─ BLUEPRINT VM ────────────────────────────────────────────┐
│  designers' bytecode, interpreted (~10× slower than C++   │
│  and it does not matter: it calls native code for the     │
│  heavy parts — exactly like your Lua calls LÖVE)          │
├─ UOBJECT SYSTEM ──────────────────────────────────────────┤
│  a managed language built inside C++: garbage collection, │
│  reflection, serialization, network replication — the     │
│  UCLASS()/UPROPERTY() macros feed a code generator (UHT)  │
│  that writes the plumbing C++ can't express               │
├─ THE WORLD ───────────────────────────────────────────────┤
│  Actors registered into tick groups; the frame is a       │
│  schedule of ticks, not one loop over one list            │
├─ ENGINE MODULES ──────────────────────────────────────────┤
│  GameThread  │  RenderThread  │  RHI thread  │  Chaos     │
│  simulates N │  draws N-1     │  talks GPU   │  physics   │
└───────────────────────────────────────────────────────────┘
Two things to notice. The UObject layer is why Unreal C++ "feels weird" — those macros aren't decoration, they generate the reflection and GC machinery. And the thread split means the render thread is always drawing last frame while the game thread simulates this one: engine-scale parallelism, hidden behind the Actor API.

Real code

// Paddle.h — inheritance is alive and unashamed: #2
UCLASS()
class APaddle : public APawn {                  // AActor -> APawn -> you
    GENERATED_BODY()

    UPROPERTY(EditAnywhere, BlueprintReadWrite) // exposed to designers: data-driven
    float Speed = 360.f;

    UPROPERTY(VisibleAnywhere)
    UStaticMeshComponent* Mesh;                 // components, layered on: #3

    UPROPERTY(BlueprintAssignable)
    FOnBallHit OnBallHit;                       // delegates: #4
};

Same count, four paradigms — but look which one is the spine here versus in Unity. In Unity you attach; in Unreal you derive, then attach.

❓ "Didn't Part 1 say inheritance breaks? Why does it survive here?"

Because Part 1's hard round was about combining abilities across branches — and the things Unreal's chain models (player characters in shooters) genuinely ARE tree-shaped: nearly every game wants "ACharacter, but slightly different," and almost none wants a Ball-that-steers-like-a-Paddle. Inheritance is a fine bet when your domain really is a tree. The cost shows at the edges: ACharacter is a famously enormous god-class, and when your game's pawn isn't a biped with gravity, you fight the inheritance instead of riding it. Betting on #2 means betting on what kind of games your engine is for — and Unreal's answer has always been clear.

❓ "Why two languages? The C++/Blueprint split seems insane."

It's the same split you're living in this course: LÖVE's C++ core underneath, your Lua gameplay on top. Engine-grade code (rendering, physics, networking) needs C++'s performance and lives with engineers; gameplay changes daily and belongs to designers, so it gets a forgiving, hot-reloadable layer. The friction is real — every studio argues about where the boundary sits — but the alternative is designers filing tickets for every tweak. Almost every big engine converges on a two-language split; Unreal just made it visual.

❓ "Where's Unreal's ECS?"

Same story as Unity, five years later: UE5 ships Mass Entity, an opt-in ECS used for exactly the workload Part 1 predicted — the crowds in the Matrix Awakens city demo, thousands of pedestrians and cars. The pattern to remember: both giants kept their core bet and added ECS as a special-purpose layer where the bulk lives. Nobody rewrites the core; they patch the red cell.

The bet bought them

  • Derive ACharacter, get a shippable networked player for free
  • Designers author gameplay without engineers (Blueprints)
  • Flow has a real home (GameMode) — no ghost managers

The bet cost them

  • The steepest learning cliff of the three
  • God-classes at the top of the hierarchy
  • Reading it is archaeology: three decades of stacked decisions
ENGINE 3/3

Godot — the contrarian bet

core bet: scene tree (#5) + signals (#4) — and a public refusal of ECS
BrotatoDome KeeperCassette Beastsopen source (MIT)

The bet

Godot (open-sourced 2014) is the deliberate contrarian: while the industry chased ECS, its creators wrote a manifesto — "Why isn't Godot an ECS-based game engine?" — and doubled down on the tree. Everything is a Node. Behavior = subclass a node (extends CharacterBody2D) and override _process; composition = give a node children; communication = signals. A "scene" is just a saved subtree you instance anywhere — so the paddle-with-a-sprite-child you built in lesson/pong/05-scenegraph is, structurally, a Godot game. The bet is explicit in the manifesto: optimize for the programmer's understanding, not the CPU's cache — and let the engine's internals worry about speed.

How it held

Unity and Unreal grew by adding paradigms. Godot's history is the opposite shape: the same bet, defended for two decades — with the pressure absorbed by the internals instead of the API.

  • 2001the ancestor — Juan Linietsky and Ariel Manzur build in-house engines for contract work in Argentina; the scenes-and-nodes idea is already forming.
  • 2014open-sourced as Godot (MIT) — the core bet arrives public and already whole: everything is a node, nodes talk by signals, scenes are saved subtrees. #5 + #4
  • 2018Godot 3.0 — the internals are formalized as Servers: flat, data-oriented rendering and physics cores behind the node façade. data-oriented inside Pain: trees are slow to traverse in bulk — so the bulk moved below the API instead of changing it.
  • 2021the manifesto — years of "why isn't this ECS?" pressure get a written answer instead of a pivot. The bet defended in public, with arguments — which is rarer and braver than quietly drifting.
  • 2023Godot 4.0 — a full rewrite of the core… and the API is still nodes. Same bet, third decade.

The composition

the core: the Node tree #5 scene graph + signals #4 events
The only engine of the three whose event system is part of the core bet, not a layer: nodes are wired by signals in the editor, exactly like our event-bus Pong.
layered on top

Under the hood

The accordion below claims the tree is the interface, not the implementation. Here's that claim as a picture:

┌─ GDSCRIPT / C# VM ────────────────────────────────────────┐
│  your scripts, attached to nodes                          │
├─ SCENETREE (the main loop) ───────────────────────────────┤
│  root ─ court ─ paddle ─ sprite …                         │
│  walks the tree calling _process(delta) — literally our   │
│  lesson/pong/05-scenegraph, industrialized                │
│  a node is a thin façade holding an RID — a claim ticket  │
│  for a resource that lives below                          │
├─ SERVERS (the real engine) ───────────────────────────────┤
│  RenderingServer │ PhysicsServer │ AudioServer            │
│  flat arrays indexed by RID — no tree down here!         │
│  nodes send commands; servers can run on their own threads│
├─ DRIVERS / PLATFORM ──────────────────────────────────────┤
│  Vulkan / GL, OS                                          │
└───────────────────────────────────────────────────────────┘
When you set sprite.position, the node forwards a command to the RenderingServer, which updates a flat array — the tree never touches the hot path. That's how the "reject ECS" engine stays fast: the paradigm debate is about the API humans see (layer 3); below it, everyone converges on flat, data-oriented arrays.

Real code

# paddle.gd — a script on a node in the tree: #5
extends CharacterBody2D

signal ball_hit                       # signals are first-class citizens: #4

@export var speed := 360.0            # shows up in the Inspector (data-driven)

func _process(delta):                 # override the node's behavior: #2, shallow
    var dir := Input.get_axis("ui_up", "ui_down")
    position.y += dir * speed * delta
❓ "Why did Godot reject ECS? Are they wrong?"

Read the manifesto — it's assigned reading, and it's a defensible engineering argument, not ignorance: most games are not crowd simulations; most gameplay code is written by people who think in scenes and objects, not in queries; and composition-by-child-nodes covers most of what component-composition buys. They chose the green cells that matter for their users (understandability, content workflow) and accepted the red ones. You don't have to agree — Bevy's designers wrote essentially the opposite manifesto — but notice that an informed team looked at ECS and said no, for reasons. That should permanently cure you of "X is always the right architecture."

❓ "Then why isn't Godot slow?"

Because the tree is the interface, not the implementation. Under the nodes sit the Servers — RenderingServer, PhysicsServer — flat, data-oriented cores that process everything in bulk, no tree in sight. Nodes are a friendly façade that forwards to them. And when you truly need 10,000 things, you skip nodes and talk to the servers directly (MultiMesh, RenderingServer API). So even the engine that publicly rejected ECS is data-oriented inside — the paradigm war is about the API you give humans, not what the machine runs.

❓ "Where does the Pokémon party live in Godot?"

Part 1's scene-graph hard round, now with the official answer: autoload singletons — scripts the engine instantiates outside any scene, globally reachable, surviving scene changes. It is global state, institutionalized, with documentation and a settings tab. Every core bet needs an escape hatch for what it can't model; the mature engines just admit it and give the hatch a name.

The bet bought them

  • The smallest mental model — one concept, nodes
  • Scenes compose like Lego; instancing is the whole workflow
  • Signals everywhere = decoupling by default

The bet cost them

  • Crowds/bulk need escape hatches (servers, MultiMesh)
  • String node paths — one rename from a crash
  • Non-scene state exiles to autoload sprawl

Pokémon, shipped

Final exercise. Through Part 1 we pushed one imaginary Pokémon game through each paradigm and watched something break every time. Now drop the constraint that it must be one paradigm — architect it like an engine team would, subsystem by subsystem:

overworld simulation #6 ECS
Hundreds of NPCs, tall grass, ledges, the player — crowds of uniform things. Bicycle = one component + one system.
battle flow state machine + data tables
Intro → menu → move → animation → damage → faint check: strictly sequential, exactly two combatants. Plain explicit states — like fsm in the hybrid demo below. Species, moves, and trainers are rows in tables (data-driven), not code.
abilities & items #4 events
"WHEN hit by a contact move, DO 30% paralysis" — handlers on the battle's event stream, one subscriber per ability.
camera, menus, dialog #5 scene tree
Spatial and nested: the camera rides the player, the dialog box rides the UI layer.
Four paradigms, one game, zero contradictions — each subsystem gets the architecture whose green column it lives in. Architecture is chosen per subsystem, not per game.

Proof it composes — Pong number seven

love lesson/pong/07-hybrid

One last Pong: ECS simulates the court, systems announce facts on an event bus, and an explicit state machine owns the match flow (serve delay → play → game over) — Part 1's ECS hard question, answered in code. The boundaries are the whole lesson:

-- systems DETECT and announce [ECS -> EVENT]:
registry.destroy(ballEntity)
Bus.emit("ball:out", out)          -- who scores? not my job

-- handlers DECIDE [EVENT -> FSM]:
Bus.on("ball:out", function(side)
    if side == "left" then match.right = match.right + 1
    else match.left = match.left + 1 end
    if match.left >= 5 or match.right >= 5 then
        fsm.enter("gameover")
    else
        fsm.enter("serve", side == "left" and -1 or 1)
    end
end)

-- the state machine SEQUENCES [FSM]:
states.serve = {
    update = function(dt)
        if fsm.time > 0.8 then
            spawnBall(states.serve.direction)
            fsm.enter("play")
        end
    end,
}

Press B: the ECS half still shrugs at extra balls. Score the fifth point: the state machine reads like a sentence. Each paradigm kept its green cells; none was forced into its red ones.
